# SDK migration — Phase 0 report

Phase 0 establishes measurements and safety boundaries only.  It makes no
functional move, public API change, package-manager migration, or production
configuration change.

## Reproducible graph

The graph starts at
`browser-extension/backend/service-worker/orchestrator.ts` and is stored in:

- `docs/sdk-migration/graph.json` — Madge transitive TypeScript graph.
- `docs/sdk-migration/dependency-cruiser.json` — dependency-cruiser graph.
- `docs/sdk-migration/deps.dot` and `docs/sdk-migration/deps.svg` — rendered
  dependency graph.
- `.dependency-cruiser.js` — repeatable resolver configuration, including the
  extension TypeScript and webpack aliases.

Madge found 51 nodes and 101 edges in the entrypoint closure.  The broader
dependency-cruiser run found 182 modules and 474 dependencies.  TypeScript and
the extension webpack configuration resolve every `@lib/*` and
`@background/*` import.  The one remaining dependency-cruiser unresolved edge,
`../wasm/policy_engine_wasm`, is generated by the WASM build and consumed by
`wasm-bridge.ts`.

Ownership rule: a source file is **host** if it directly or transitively reaches
`webextension-polyfill`, `chrome.*`, `browser.*`, or `Browser.*`; otherwise it
is **core**.  The direct browser-API scan ignores comments and string literals.
On that rule, the entrypoint closure is 21 core files / 4,874 LOC and 30 host
files / 9,224 LOC (51 files / 14,098 LOC total).  This is an observed baseline,
not a proposed package manifest.

## Boundary review

`bundle-verify.ts` is core under the browser-API rule, but it relies on
WebCrypto and an injected `fetchImpl`; Phase 1 must decide whether the SDK
exposes that as a capability/port rather than assuming a browser runtime.
`wasm-bridge.ts` is also core by the same rule but consumes a generated WASM
artifact.  It is an SDK packaging boundary, not a browser-host module.

`browser-extension/sdk/extension-client.ts` is outside the service-worker
entrypoint closure.  It is a dashboard/extension transport that uses window
messaging and Chrome runtime plumbing, so it is host code.  The pure `block-ir`
modules and `policy-store-types.ts` need a public-surface decision before they
are exported from an SDK.

## Browser-free verdict baseline

`fixtures/baseline-verdicts.test.ts` initializes the real compiled WASM module
in Node, reads its input policy set from
`browser-extension/public/default-policies/policy-set-v2.json`, and compares
the real engine envelope to `fixtures/baseline-verdicts.json`.  It does not
construct `window`, `chrome`, `browser`, or a WebExtension mock.

The four cases freeze `submitted_at` at `1738000000` and cover bounded
approval (pass), unlimited approval (warn), burn-address transfer (fail), and
opaque call (warn).  The fixture pins the policy-set SHA-256
`f6cfe0094c3c209f8ea47c970289efeceeb3fa56ecedad24b1f65301f75d0765`.
`fixtures/normalize.ts` recursively sorts object keys and removes only known
diagnostic observation-time fields.  It does not discard semantic transaction
time fields.  The current engine envelope contains none of the removable
fields; `durationMs` is emitted only by the extension bridge debug log at
`wasm-bridge.ts:419-458`.

## Package-manager integration plan (approval required)

The root uses Yarn 4, the browser extension has its own Yarn lockfile, and
`registryV2`/`registry-api` retain npm lockfiles.  The recommended Phase 1
sequence is to make the root Yarn workspace authoritative for `packages/*` and
the intended browser apps, migrate the intended `apps/registry-api` as a
deliberate lockfile transition, and retain `registryV2` as an explicitly
independent npm island unless its ownership changes.  That lockfile work is
deferred: Phase 0 neither removes nor regenerates a project lockfile.

## Unplaced directories — choices needed before Phase 1

| Directory | Recommended disposition | Alternative that needs approval |
| --- | --- | --- |
| `registryV2/` | retain as independent private npm registry-data project; inject data into core through a port | migrate into the root Yarn workspace |
| `schema/` | retain as canonical repository build input; package generated/embedded artifacts intentionally later | promote it to a public core data contract |
| `scripts/` | retain at root as repository tooling | relocate under a new `tools/` convention |
| `request-module/` | retain as a legacy/example module until a maintained userscript product is chosen | make it a private userscript app or an SDK integration example |
| `browser-extension/sdk/` | keep `extension-client.ts` as host transport; choose an internal SDK surface for pure IR/types | introduce a separate private dashboard-authoring package |

## WASM packaging decision needed before Phase 3

| Target | ESM/CJS fetched artifact | UMD inline base64 artifact | Current implication |
| --- | --- | --- | --- |
| `@dambi/core-wasm` | natural fit | no | keeps the raw 8.06 MB binary external |
| `@dambi/core-wasm-umd` | optional fallback | required if offline single-file is promised | adds a 10.74 MB base64 payload before compression |

The suggested dual-package approach is technically feasible, but its current
WASM gzip size is 2.50 MB.  Approval is needed to treat that as an accepted
budget exception, change the budget's definition, or choose a different
packaging target.
